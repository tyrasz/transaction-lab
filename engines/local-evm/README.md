# Experimental local EVM execution

Version 0.26 enables Ethereum EIP-4844 point evaluation on the pinned Cancun-through-BPO2 forks. The earlier unsupported-KZG descriptions below record prior release boundaries; the current point-evaluation scope and failure handling are described at the end of this document. Blob sidecar validation remains outside support.

This package executes bytecode locally using pinned EthereumJS 10.1.3 packages. It powers Transaction Lab's independent local-preview API and browser option, alongside the separate provider-backed engine. It includes the original HyperEVM development profile and a new Ethereum mainnet reference with proof-verified initial state. Neither profile is a signed-transaction validator or security classifier. [Upstream EVM documentation](https://github.com/ethereumjs/ethereumjs-monorepo/tree/master/packages/evm).

From the project root:

```sh
npm ci --prefix engines/local-evm --ignore-scripts
npm run test:local
```

Dependencies and integrity hashes are pinned in this package's lockfile. The primary service's dependency-free runtime remains unchanged.

## Ethereum reference

The independent input path uses `verifyEthereumHeader({header,expectedHash})`, `createRpcStateInputs({chainId:1,blockHash,header,rpc})`, `createProofStateManager({inputs})`, and `executeEthereumCall({request,header,stateManager})`. The request contains `{from,to,data,value,gas,accessList?,blobVersionedHashes?,authorizationList?,executionProfile?,fees?}`. Callers retain the header verification and input-proof evidence alongside the execution result; the executor alone does not claim to authenticate its state manager.

The header verifier recomputes the exact RLP/Keccak execution-header commitment, including the active Shanghai, Cancun and Prague fields. It binds the state root and execution fields to an externally selected block hash. It does not verify consensus, finality, chain membership or transaction/withdrawal bodies. The collector fetches `eth_getProof` and `eth_getCode` at `{blockHash,requireCanonical:true}`, plus parent headers by authenticated hash when execution requires them. Account and requested storage paths must verify against that root; runtime bytes must match the proven code hash. Account/slot exclusion is distinct from missing data. Geth's zero-hash metadata for a proven absent account is retained separately from normalized absence facts. [EIP-1186](https://eips.ethereum.org/EIPS/eip-1186), [header field order](https://eips.ethereum.org/EIPS/eip-4788), [requests commitment](https://eips.ethereum.org/EIPS/eip-7685).

State is fetched lazily when local bytecode demands it, including prior values before writes. No provider trace, poststate or expected output supplies those inputs. Immutable proven facts survive nested rollback; mutable writes do not. Proven absent accounts support ordinary native funding and unsigned-sender nonce materialization. A zero-value touch preserves absence. Authenticated existing empty accounts follow the transaction-end cleanup described below. Internal CREATE/CREATE2 can install runtime code and initialize storage when the target has a proven empty initial code/storage state and zero nonce. Prefunded targets preserve their balances. Creation markers follow nested checkpoints; constructor failure or a parent revert removes their code, storage and funding. General runtime replacement, unknown storage clearing and arbitrary account deletion remain unsupported. The bounded Cancun finalizer below can delete authenticated contracts created in the current invocation.

The Ethereum wrapper selects the pinned mainnet fork by both block number and timestamp, from Shanghai through BPO2. It subtracts intrinsic gas before execution, checks the active calldata-floor admission rule, then reports gas with the one-fifth refund cap and applicable floor. Sender code, native-value affordability and nonce overflow are checked before any message mutation. ETH transfers, self-transfers, reverting child value and existing destination delegation have synthetic controls. Active precompile warming follows the selected fork. Actual source BASEFEE remains separate from the unpriced execution's zero BASEFEE/GASPRICE. No fees or outer signatures are processed. [EIP-7623](https://eips.ethereum.org/EIPS/eip-7623), [EIP-3529](https://eips.ethereum.org/EIPS/eip-3529).

Ethereum execution has a 120-second cooperative limit to accommodate bounded proof reads, with the original five-million-gas, instruction, call-depth and memory ceilings. The collector also enforces its own call, byte and time limits; its byte accounting describes parsed results, so the supplied transport must bound response bodies before parsing. It performs no retries or alternate-state fallback. Proofs do not establish a recomputed poststate root or complete economic-effect inventory. In-range `BLOCKHASH` follows the verified source header's parent chain. The immediate parent hash requires no additional read; older ancestors are fetched by the previously authenticated parent hash, with header hashes and sequential numbers checked. Reads share existing budgets, so missing or over-budget ancestry is unavailable. Rematerialization after deletion of original code, nonzero nonce or a nonempty storage trie and non-delegation coded senders remain outside this reference profile. Point evaluation is supported with the version 0.26 scope below. Declared blob context is supported under the unsigned zero-blob-fee profile described below. Operating-system isolation is not yet implemented.

Version 0.15 preserves optional access lists through the isolated worker and charges 2,400 gas per address occurrence plus 1,900 per storage-key occurrence, including duplicates. Warming uses sets and survives nested rollback. Explicit Cancun-or-later blob hashes enable `BLOBHASH` and synthetic-zero `BLOBBASEFEE`; no blob fee settlement, sidecar or KZG validation is performed. On Ethereum after Cancun, `BLOBHASH` without declared blobs returns zero, including in fresh getter calls. Before Cancun it remains an invalid opcode. `BLOBBASEFEE` without declared blob context remains unsupported. The limit of 32 declared hashes is a bounded simulation input, not signed-transaction admission. Before/after getter calls receive fresh contexts without the original access list or blob hashes. The broker independently binds exact context arrays, gas and profile fields. [EIP-2930](https://eips.ethereum.org/EIPS/eip-2930), [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844).

That failure is preserved. This tests selected input capabilities, not transaction accuracy or provider infrastructure independence.

## Original HyperEVM input and execution boundaries

`prestate-inputs.js` accepts only a captured pre-execution state, explicitly observed missing account-field completions, the declared call and its selected block. The interface has no provider trace or post-state input. It subtracts calldata-derived intrinsic gas from the declared gas budget using the explicit Cancun call rule. Actual block base fee and the selected synthetic zero-base-fee execution profile remain distinct.

`recorded-state.js` implements an isolated sparse state manager. Known zero values and missing facts are distinct. Missing accounts, code or storage slots stop execution; missing prior values also stop writes. Copies and checkpoints preserve input facts through nested reverts. Reads remain recorded even when execution rolls back. No network fallback can fill an unknown value. The adapter does not provide a state root or cryptographic proof.

`execute.js` executes real bytecode with explicit chain ID 999, Cancun rules, caller/origin and warm-address policy. It returns message gas, refund counter, call tree, committed logs and execution limits. Completed message calls retain their sender nonce behavior; unsupported behavior, missing state and host/limit failures roll back the worker's changes. Contract creation, destruction, HyperCore read precompiles, CoreWriter, blob context and unprovided in-range BLOCKHASH values remain unsupported.

The worker's deadline is cooperative. Supplied state/block adapters must bound their own asynchronous operations. This recorded adapter performs no I/O during execution; the experimental executor is not yet a separate operating-system process for hostile workloads.

## Process-separated Ethereum calls

`executeIsolatedEthereumCall({request,header,rpc,limits?,signal?})` verifies the supplied header, then starts the fixed `isolated-worker.js` with a 256 MiB V8 old-space ceiling. The parent brokers canonical same-hash `eth_getProof`/`eth_getCode` reads and sequential hash-authenticated parent-header reads. The child receives no endpoint, provider trace, expected output or expected poststate. The external `rpc.call(method,params,{signal})` must capture and bound actual wire bytes; IPC result sizes describe parsed JSON separately.

The default process deadline is 145 seconds, with up to 25 seconds of bounded read drain and one second of kill confirmation. Process failure withholds all asserted execution/state output. A completed child can still report unavailable or unsupported EVM execution. Late responses cannot restore success or mutate returned records. No automatic retries occur. This is a process boundary and V8 old-space cap, not an OS network/filesystem sandbox or hard total-RSS limit; runtime source binding remains the runner's responsibility. The parent independently reconstructs the returned ancestry evidence from its own received headers.

The local suite checks process/protocol controls, proof rejection, lazy state rollback, fork/gas boundaries and saved public proof packets. Actual workers reproduce the archived one-unit USDC call and selected Aave/Morpho previews. These are regression and development checks, not independent transaction observations or an accuracy percentage.

## Owned before/after preview

`executeIsolatedEthereumPreview({request,header,rpc,queries,limits?,signal?})` uses the same fixed process and parent proof broker. It executes the original call once, retains its output and full observed state overlay, then measures one to eight explicit query pairs. Before probes start from verified initial facts; after probes copy the entire original overlay. Each probe has a disposable state manager, the original sender, zero value and one million declared gas. It cannot carry a query nonce or other write into the original state or another query.

Canonical `balanceOf`/`allowance` calls and typed Aave V3 user-account-data/Morpho Blue position declarations share a strict compiler and ABI decoder. Identities retain the token/account, owner/spender, or contract/user/market. Raw integers and tuple units stay explicit; decimals, contract identity and oracle base currency are not independently established. Net query mutations may contain only the expected sender nonce increment and no committed logs. This is a net-state check, not STATICCALL enforcement or proof that no write opcode ran.

The original and all probes share proof, response, execution, trace and time ceilings. Root return-byte totals and retained trace bytes (including descendant outputs) are separate counters. The host rechecks query declarations, decoded amounts/deltas, original context, proof-broker evidence, state overlays and execution counters before accepting the child result. Process/protocol failure withholds the whole preview; a later missing proof can leave earlier measured pairs and the original execution intact, with the failed and unattempted pairs explicit.

The offline recorded tests reuse the independently captured lending proofs, never provider traces or expected poststate as execution inputs. Three Aave queries and eight Morpho queries reproduce exact before/after raw values. Morpho's eight-query case also passes through the actual child after its 230 recorded proof/code reads, preserving wallet, wrapper, inner vault, Blue custody and fee-recipient identities. Missing Aave aToken or additional position-query proofs remain unavailable; new public input capture is still required. These are selected development examples, not fresh coverage observations.

The internal `executeEthereumPreview` core is also exported for tests, with flat tighten-only `ETHEREUM_PREVIEW_LIMITS`. It has a cooperative deadline and explicitly reports no process isolation. Use the isolated host for process termination and provide a transport that bounds and captures actual wire bytes. The independent API and browser mode expose this preview alongside the provider path. Owned native-asset summaries, automatic query discovery, sequential call previews, security verdicts and a complete economic inventory are not added by this module. The explicit 0.24 profile below adds fee settlement for the original call.

## Internal creation result checks

The isolated parent independently reverifies referenced account/storage proofs and code hashes against its joined transport replies, reconstructs the claimed immutable facts, and validates every returned overlay against those facts. Every completed call increments the sender nonce once, then adds accepted self-authorizations and committed creation attempts. Root reverts/failures retain authorization preparation and the outer increment, plus any authenticated RIPEMD160 empty-account cleanup. A retained deployment must have a successful CREATE/CREATE2 frame with no reverted ancestor, a matching runtime-code output, a zero initial nonce and proven empty code/storage roots. Every surviving committed creation must remain represented in final changes. Finalized deletion is an explicit exception, bound to committed SELFDESTRUCT evidence and the header-selected fork; Cancun-or-later additionally requires creation within the same invocation. Disposable getter checks preserve all original creation/code/storage and finalized-deletion rows and allow only their expected sender-nonce increment. These are consistency checks over fixed-worker output, not a second execution engine or a recomputed poststate-root proof.

The chain-1 local route supports this bounded creation slice; the provider-backed measurements and general cohort comparator still reject lifecycle changes. Version 0.17 also supports explicit `to:null` top-level CREATE and Cancun-or-later SELFDESTRUCT on contracts that predate the current invocation. Regression coverage includes nested deployment, execution of fresh code inside a constructor, prefunded targets, empty runtime, constructor faults, CREATE2 collisions, static-call faults and outer rollback after a child commits.

## Direct deployment and Cancun finalization — 0.18

Use explicit `to:null` with initcode in `data` for a top-level deployment. Missing destinations and root CREATE2 salts are rejected. The unchanged product limit is 32 KiB initcode and five million total gas. Intrinsic accounting includes 32,000 creation gas and EIP-3860 word cost, plus calldata/access-list charges and the applicable Prague floor; runtime-code deposit gas is charged by execution. Blob context requires a call destination. The parent independently derives the deployment address from the sender’s verified initial nonce, checks runtime/state claims, and distinguishes `top_level_contract_creation` from internal creation. Failed constructors retain only the unsigned sender nonce increment; unavailable inputs or host limits roll the entire attempt back.

For Cancun-or-later contracts that predate the invocation, SELFDESTRUCT transfers native balances while code, storage and nonce survive; self-beneficiary preserves its balance. DELEGATECALL uses the execution account rather than the code address. The guard uses the VM’s current invocation creation set, not persistent overlay provenance: a contract created by the original call is preexisting in a later disposable query. Query mutation checks still reject any net writes besides the expected query sender nonce. Version 0.19 adds EIP-161 cleanup under the unsigned profile below. Version 0.20 supports the earlier Shanghai deletion behavior in its own fork-selected path. These rules follow [EIP-6780](https://eips.ethereum.org/EIPS/eip-6780).

Lifecycle metadata describes encountered operations; ordinary Ethereum calls report `no_lifecycle_operation_encountered`. The original state proof, return bytes, logs, gas and state deltas remain separate from this descriptive field. Parent checks also bind completed execution status to the actual error classification, preventing a reverted/failed constructor from being relabelled successful in child output.

Version 0.18 finalizes deletion when the committed root SELFDESTRUCT map and invocation creation set both contain an account. Finalization runs inside the outer checkpoint after successful root execution. The entire account, code and storage are removed, including any balance sent back after SELFDESTRUCT; no zero-balance precondition is imposed. The initial target must have a proof-verified zero nonce, empty code and empty storage trie. Reverts or host failures roll back the finalization with the rest of the attempt.

Successful own-frame observations carry `selfdestruct: {beneficiary}`. Nonempty `output.lifecycle.finalizedDeletions` lists the exact committed creation/destruction intersection. The parent rejects omissions, extras, duplicate addresses, reverted-ancestor claims and inconsistent initial proofs. An initially absent created/deleted target has no net changed-account row. A prefunded target instead has `existence: {before:true,after:false,basis:'same_invocation_created_contract_deletion'}` and its original positive balance changing to zero; original nonce/code/storage were empty. Surviving creations retain the existing runtime and state checks.

Deletion/reset markers follow checkpoint, rollback and copy operations. After-state queries cannot resurrect deleted code or storage from immutable initial facts, and a deleted account can be funded or redeployed in a later invocation only under the same proof and lifecycle restrictions. Query checks compare net before/after snapshots, so original deletion rows persist and any new transfer, surviving account or creator nonce change remains a mutation. Transient activity is not inferred to be a pure read. These controls use synthetic authenticated state and real child execution; they are not a new public-chain coverage observation.

## Empty-account cleanup — 0.19

The Ethereum route now admits authenticated existing empty accounts and runs the pinned EVM journal's EIP-161 cleanup after each completed message, inside the outer rollback checkpoint. Empty means zero nonce, zero balance and empty code; storage may be nonempty. Cleanup removes the entire account and storage trie. Read-only BALANCE or access-list warming does not touch an account. Ordinary reverted touches are discarded; the pinned RIPEMD160 touch exception survives child and root reverts. No fee settlement or fee-related coinbase touch is added to this unsigned profile. [EIP-161](https://eips.ethereum.org/EIPS/eip-161).

Actual removals appear in `lifecycle.emptyAccountCleanup`, with retained journal touches, whole-account scope and each authenticated initial storage root. Net rows use `existence: {before:true,after:false,basis:'eip161_empty_account_cleanup'}`; they do not pretend to enumerate unknown storage. The parent derives required cleanup from bound call contexts, verified starting facts and bounded native-value flow. Fabricated nonce or balance changes cannot suppress required deletion. A root revert normally retains only the sender nonce; authenticated RIPEMD160 cleanup is the explicit exception. Disposable queries preserve carried cleanup and still reject mutations.

Cleanup executes through a guarded deletion window, and its reset markers survive copies and roll back on host failure. Unknown slots in a deleted account read zero without fetching or resurrecting prior storage. Retaining a rematerialized account with original code, nonzero nonce or nonempty storage remains unsupported until the net-change schema can represent that reset; initially deployable targets retain the earlier funding/recreation behavior. Version 0.20.1 allows temporary native funding inside an active checkpoint when an enclosing EVM revert removes it before the invocation ends. Signed transaction preprocessing and fees, and full consensus validation remain outside the profile. Synthetic controls and retained-input replays are regression evidence, not an all-EVM accuracy rate.

## Historical Shanghai deletion — 0.20

For verified Shanghai headers, every committed SELFDESTRUCT execution account is removed at transaction end. Its code, nonce and entire storage trie are removed, including slots never demanded by the sparse proof reader. A self-beneficiary burns its balance immediately; code/storage remain available to later calls within that transaction, and finalization burns any later refill. The same opcode on Cancun-or-later preserves a preexisting account. The parent chooses this distinction from its trusted header, rather than accepting a child-supplied fork claim. [EIP-6780](https://eips.ethereum.org/EIPS/eip-6780).

Shanghai uses the existing `lifecycle.finalizedDeletions` row shape with the authenticated original storage root. An initially existing account has `existence: {before:true,after:false,basis:'shanghai_selfdestruct_deletion'}` plus its original positive balance becoming zero when applicable. Whole-account removal subsumes nonce/code/storage; the output does not invent per-slot coverage. An initially absent created/deleted target has no net row. Delegated destruction concerns the execution account, and reverted ancestors cannot authorize removal.

Finalization and EIP-161 cleanup share the outer atomic checkpoint. Host failures or limits discard the whole attempt; EVM reverts retain only allowed nonce and sticky-cleanup effects. Query copies retain reset markers and cannot fetch old code or storage back into existence. New query deletions are mutations and withhold the measurement. General provider-backed lifecycle measurements remain unchanged.

## Reverted funding of deleted accounts — 0.20.1

An after-state getter can temporarily send native value to an account removed by the original call, catch an enclosing subcall revert, and return a stable value. Previously the first temporary balance write aborted the whole query, even though the EVM would have rolled it back. Such writes now follow the normal nested checkpoints. Deleted code and all original storage remain masked throughout execution.

Before retaining the invocation, a state guard rejects any surviving rematerialization whose original code, nonce or storage would require whole-namespace reset provenance. The same guard protects snapshots and the manager's outermost commit; it does not run at nested message commits. A rejection restores the whole invocation, including the sender nonce, and preserves any caller-owned checkpoint. Creation restrictions and the net-change schema are unchanged. Query measurements still require the existing independently checked nonce-only net changes.

## Existing delegated senders — 0.21

The authorization extension in 0.22 preserves the original no-list behavior described here.

On Ethereum Prague or later, a sender with exact 23-byte `0xef0100 || address` code can originate an unsigned call or deployment. Both child admission and parent validation use the proven sender code and header-selected fork. This implements existing delegation under [EIP-7702](https://eips.ethereum.org/EIPS/eip-7702). Version 0.22 adds the separate authorization preparation described below. Other runtime-code senders remain unsupported.

A delegated wallet can execute in its own account context, including through callbacks, DELEGATECALL and CALLCODE. The nonce includes the outer transaction increment plus entered CREATE/CREATE2 attempts whose parent ancestry commits. A reverted constructor or collision retains its creator increment; a reverted enclosing call removes it. The child checks the final nonce before retaining state, and the parent independently derives the count from bounded execution frames. Current supported forks stop at BPO2; later fork changes to creation ordering require separate support. Merely originating a transaction does not warm the implementation. Root destination delegation receives the EVM's prescribed warming.

Disposable queries still permit only their expected single sender-nonce increment and no other net mutation. A getter that creates a contract from the sender cannot become a measured result. Twenty new execution/parent controls include exact gas, return, logs and independently applied full-MPT roots against a signed zero-price full-VM counterpart. Those controls share the opcode library and do not establish population accuracy.

## Ordered authorizations — 0.22

The local API and Ethereum kernel accept optional `authorizationList: [{chainId,address,nonce,yParity,r,s}]`. Supply one to sixteen tuples with canonical hexadecimal quantities and a 20-byte destination. Structural limits are uint256/20 bytes/uint64/uint8/uint256/uint256. Preserve order and duplicates. Prague-or-later calls support this field; root deployment and blob context cannot accompany it. The outer transaction still has no signature; fee settlement requires the explicit 0.24 profile below. The provider-backed routes do not gain authorization support.

Each tuple pays 25,000 intrinsic gas, including protocol-skipped entries. After the outer sender increment, the executor validates the authorization signature, chain, current code and nonce. A recoverable authority is warmed even if its code or nonce causes a skip. Accepted tuples install, replace or clear the exact delegation without resetting storage or balance. Refunds use account existence at that point, following the [official execution specification](https://github.com/ethereum/execution-specs/blob/master/src/ethereum/forks/prague/vm/eoa_delegation.py) and pinned clients; an existing empty account differs from an absent account. The message refund stays in `execution.gasRefundCounter`; `authorizationProcessing.gasRefundCounter` is separate. Their sum enters the transaction refund cap and calldata floor.

Authorization nonce/code changes survive message REVERT or out-of-gas. Missing proofs, host errors, unsupported behavior and deadlines restore the entire attempt. Completed results expose every applied/skipped tuple and a closed reason code. The parent independently recovers authorities and folds ordered decisions over reverified initial facts, then checks metadata, code, exact nonce changes, materialization and refunds. This also rejects invented nonce increases for skipped authorities. An absent authority uses `eip7702_authorization_materialization`; it does not become an EIP-6780 constructor creation.

Before probes use original state; after probes retain authorization preparation and message effects, including preparation after a reverted message. Neither probe receives the authorization list. The parent checks each probe's actual starting sender code and still permits only that probe's expected single nonce increment. These are bounded consistency and differential-execution checks, not complete economic interpretation or a universal accuracy guarantee.

## Caller-selected gas — 0.23

The local HTTP API forwards optional canonical decimal `gas` for the original transaction, including intrinsic gas. It defaults to 5,000,000 and accepts 21,000 through 5,000,000; the verified fork also enforces access-list, authorization, deployment and calldata-floor admission costs before proof reads or child execution. `apiRequest.gas` records the effective limit. GAS and out-of-gas behavior use that limit; completed EVM failures retain only their permitted outer preparation, with message writes rolled back. Before/after queries keep separate 1,000,000-gas contexts. Execution, read, output and time ceilings remain unchanged. The provider-backed routes keep their existing fixed gas profile. This adds no fee settlement, original-position replay or broad accuracy claim.

## Explicit EIP-1559 pricing — 0.24

An optional `executionProfile: "unsigned_eip1559_block_end"` and `fees: {maxFeePerGas,maxPriorityFeePerGas}` price the original unsigned transaction using canonical decimal wei strings and the verified source block base fee. Both fields are required together; partial profiles, unknown fee fields, priority above cap and blob context are rejected. Admission checks the cap, block gas limit and maximum affordability; the default unpriced profile remains unchanged.

Inside one outer checkpoint, the executor prepays effective gas cost, prepares nonce/authorizations, executes the message, applies the refund cap and calldata floor, refunds the sender, credits the beneficiary even for a zero tip, finalizes SELFDESTRUCT and cleans empty accounts. Message REVERT/OOG retains fee and authorization preparation; host/proof/timeout failures roll everything back, including fees, and expose no completed accounting. The parent independently derives admitted amounts from the header and proven sender balance, checks fee records and the complete bounded native-value ledger, and rejects invented or omitted fee deltas. This is consistency validation over a fixed worker, not a second opcode implementation.

Completed `feeAccounting` separates charged gas, effective price, upfront debit, sender refund, base-fee burn and beneficiary tip. A credited tip can subsequently burn during deletion, so fee allocation and surviving balance changes remain separate. Before/after measurement calls keep unpriced one-million-gas contexts and never repeat fee settlement or authorizations. Outer signature/explicit nonce validation, original-position replay and blob fee settlement remain outside this profile.

The [frozen sixteen-case Geth fee check](../../research/delegated-sender-geth-v1/fee-controls/NOTES.md) retains fourteen matches and two failed assertions. Both failures display matching intermediate roots but stop in Geth persistence when deleting an initially empty account with hidden storage; a separately declared two-state diagnostic exposes the discarded commit error. Reachability of that synthetic prestate on mainnet is unestablished. The original failures and unestablished log assertions remain unchanged. An independent artifact audit and eight tamper/relocation controls verify the retained packet. No representative accuracy percentage is inferred.

## Explicit blob pricing — 0.25

`executionProfile: "unsigned_eip4844_block_end"` requires all three canonical decimal uint256 caps in `fees: {maxFeePerGas,maxPriorityFeePerGas,maxFeePerBlobGas}` and a nonempty ordered version-01 `blobVersionedHashes` list. It requires a call destination and rejects authorizations. Structural admission permits at most nine hashes; header-selected Cancun permits six, Prague nine, and Osaka/BPO1/BPO2 six. The corresponding block maxima are six, nine, nine, fifteen and twenty-one. Header `blobGasUsed` must be aligned and within that fork's block maximum, but is not subtracted from a constructed block-end call's allowance. This is not whole-block admission.

`ethereum-blob-fees.js` derives price from verified-header `excessBlobGas` with the exact integer exponential and selected fork update fraction. It checks uint64 header quantities and fails closed when the price exceeds uint256 or the bounded iteration budget. EIP-7918 changes the parent-to-current excess calculation; it does not add a direct BASEFEE/16 clamp to the current-header price. This module does not validate the parent excess transition, consensus or block body. See [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844), [EIP-7691](https://eips.ethereum.org/EIPS/eip-7691), [EIP-7918](https://eips.ethereum.org/EIPS/eip-7918) and [EIP-7892](https://eips.ethereum.org/EIPS/eip-7892).

Maximum affordability includes execution gas times its cap, blob gas times its cap and transferred value. Actual prepayment uses effective execution price plus actual blob burn. Execution refunds and beneficiary tips exclude blob gas; blob burn survives completed message REVERT/OOG.
