# Sealed fee comparison and two failed Geth assertions

This note is a post-capture supplement, outside the original manifest. The fixed sixteen-case capture retains **14 matched, 2 mismatched, 0 unavailable, 0 unattempted**. No case was replaced or rerun, and no captured byte or binary was changed. The two failures remain failures; their displayed roots are not enough to turn them into passes. This is synthetic development evidence, not a population accuracy rate.

The [results](capture/results.json) record a complete, usable packet with unchanged sources and no fatal error. The plan SHA-256 is `d5ae96b7f621ab2d5f3206e0068f65313deeb1cf308d97c02ca22c00f0586c68`, source manifest `29e1761097cef073599c05e41c75acce45cdb78f8429c8dde78a4f68f691df86`, and evidence manifest `43d8d063d06ceea69ef3ef3f4a71cac0c227f47fc32c1993212af8fd7b5b6d7a`. Product baseline is `d9251793d2ca7c3dccdfffeb6de51da83b306445`. Geth comparisons cover the product-applied full poststate root and the state-test runner's internal log assertion, not separately reported gas, return data or receipts.

Cases [007](capture/raw/007.json) and [008](capture/raw/008.json) each begin with coinbase `0x9999999999999999999999999999999999999999`, zero nonce/balance, empty code, and storage slot 991 containing 91. Their tip is zero. Case 007's message succeeds; 008's message reverts. The product deletes this empty, touched account including its storage. The separately executed full VM and third MPT agree with that deletion.

Both raw Geth processes exit zero but report `pass:false`. They display the same root as the product, while their error says the compared root was all zero:

The pinned Geth source explains this apparent contradiction. All anchors below refer to commit `1df30b18d9ed35ee9d28ffd4648442c2204554ad`:

1. [`stateObject.AddBalance`](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/core/state/state_object.go#L486-L495) touches an empty account even for a zero increment. [`Finalise`](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/core/state/statedb.go#L798-L809) then removes the EIP-161-empty account and records its original state for deletion.
2. [`handleDestruction`](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/core/state/statedb.go#L1244-L1254) rejects deleting a preexisting nonempty storage trie under Cancun rules, returning `unexpected storage wiping`. Osaka includes those rules. [`Commit`](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/core/state/statedb.go#L1464-L1469) returns a zero hash with that error.
3. [`StateTest.RunNoVerify`](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/tests/state_test_util.go#L361-L374) discards the commit error and returns the zero root with a nil error. [`Run`](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/tests/state_test_util.go#L257-L266) consequently reports a root mismatch and returns **before checking the log hash**.
4. The CLI callback separately calls [`IntermediateRoot` with empty fork rules](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/cmd/evm/staterunner.go#L132-L138) to populate the displayed `stateRoot`. That intermediate root can equal the product even though the earlier commit failed.

This is a source-path diagnosis from the retained inputs/results and pinned source; the underlying commit error was not emitted by the captured CLI. It identifies a concrete discarded-error problem in the Geth state-test path, and a storage-deletion invariant that this synthetic allocation exercises. It does not establish a different EVM intermediate poststate, a successful persistent Geth transition, or a successful log assertion for either failed case. The retained comparison's `internalLogHash:false` must not be read as proof that Geth actually compared and found different logs.

The inspected source hashes match the pinned source inventory: `core/state/statedb.go` SHA-256 `bffcab7175078d9000dcfa97dcb8a78cac65ce98d77ed455ca9a0602d2821b11`; `tests/state_test_util.go` `61f5097513e5874ed800a412bfd3e1f9ab4373fbfb994a59d57ba589fbc44401`; `cmd/evm/staterunner.go` `8a474f9396502e813719198fb9ae6f082717c2562ecc8a46378fe9d1036bb388`. Their source inventory SHA-256 is `36e245fda711de52fe5e0b8c917d4bbbffd840ed7edfc0696f29cbb1f8b24dff`.

Mainnet reachability is **unestablished** here. [`MakePreState`](https://github.com/ethereum/go-ethereum/blob/1df30b18d9ed35ee9d28ffd4648442c2204554ad/tests/state_test_util.go#L534-L554) accepts the arbitrary allocation and materializes it outside fork transition rules. Modern contract creation starts at nonce 1, and authorization application increments nonce even when clearing delegation; those mechanisms do not ordinarily produce a zero-nonce, code-empty account with storage. They do not prove that historical pre-EIP-161 leftovers cannot exist. This note therefore neither labels the allocation a verified reachable mainnet state nor claims that it is structurally forbidden as an arbitrary state-test prestate.

The separately reviewed and frozen [direct commit diagnostic](commit-diagnostic/NOTES.md) has now corroborated that error in one invocation containing two fresh-state controls. Changing only coinbase storage to empty permits commitment of the same intermediate root. No transaction, VM, original statetest or public RPC was executed. Its evidence manifest is `632afe5700855360c634b390b2bd97f2ffa87c584ebe966607083d8a593ac4ed`. The original 14/2 outcome and the uncertainty about mainnet reachability remain unchanged.
