# Amsterdam creation attempts — development checkpoint

The proof-backed development engine now admits the previously rejected repeated CREATE2 collision. Under EIP-7928, the second attempt increments the creator nonce without entering a constructor. The executor observes the actual successful nonce write, subsequent target read, entered child if any, and returned stack result. Each Amsterdam frame carries an explicit bounded `creationAttempts` array. Zero-write failures are omitted; host failures and evidence-budget exhaustion roll back the entire attempt.

The parent independently checks the record schema, opcode boundary in authenticated/current code, derived CREATE/CREATE2 address, child position and join, current target facts, chronological nonce updates, endowment affordability and ancestor rollback. A failed constructor retains its parent's increment; a failed parent discards descendant increments. Nested constructors, reentrancy, delegated execution and carried query state have actual execution controls. This is consistency validation of a fixed executor's evidence, not independent opcode replay. Storage-root-only collisions remain unsupported; Amsterdam sender delegation and authorization preparation remain gated.

Review found and fixed child-field accessor evaluation before descriptor validation, contradictory DELEGATECALL value, and unaffordable CALLCODE value. Amsterdam's temporary-state walk checks CALLCODE before child entry, including failed children. The historical lifecycle walk now binds DELEGATECALL value and checks CALLCODE affordability for retained successful frames; it does not claim a reconstruction of temporary historical balances beneath reverted ancestors.
