# Fixed public Arbitrum funded-example selection

This is explicit development example selection, not a representative sample or evidence of simulation accuracy. It does not revise the prior zero-balance scenario or simulate any deposit. Native Arbitrum USDC (six decimals) and the TokenMessengerV2 deployment are taken from the preserved official Circle metadata/ABI. The event and ABI are pinned to Circle commit a92a2b4e7e6ef99bf0b05dca71780f5ec190e729. No wallet ownership or signing authority is inferred from a public address.

One documented public endpoint: https://arb1.arbitrum.io/rpc (https://docs.arbitrum.io/chain-info). Request chain ID, then exactly one latest header. Query exactly one inclusive 40,000-block window ending at that header (clamped at genesis), restricted to TokenMessengerV2 and the native-USDC indexed burn-token topic. Reject malformed, removed, duplicate, conflicting-block or out-of-window logs. Sort unique depositors by descending block number, transaction index and log index. Append the original preserved public scenario sender as a known candidate if absent. Retain only the first eight in this declared order before reading their balances. No widening, fallback endpoint, retry, replacement, external address search or outcome-driven reordering.

For every declared candidate, at the same explicit block number, request USDC balanceOf(candidate), USDC allowance(candidate, TokenMessengerV2), and candidate code. Retain all three responses/errors and all candidates even after finding an eligible one. Choose the first observed candidate whose two raw uint256 values are each at least 100,000,000 and whose code was observed. Code may describe a contract or delegation; it is never removed or replaced. A failed probe remains unavailable, not zero. The selected address is only a provider-reported qualifying example; gas funding, ownership, blacklist, pausing, actual allowance spending and execution success are unestablished.

Final confirmation rereads the selected block number and requires the full returned header to be identical. Number selectors are not atomic; raw provider headers, logs and state are not cryptographic state proofs or authenticated deployment-code checks. Log authenticity and transaction success are provider observations. No destination settlement or future balance is inferred.

Limits declared before dispatch: 28 actual RPC maximum (2 selection +1 logs +8×3 probes +1 final); 4,096 logs; 4 MiB per response; 16 MiB combined decoded HTTP response bodies; 16 KiB per request; 25 seconds per request; 110 seconds for collection, reserving a call and 10 seconds for final confirmation within 120 seconds total. Pending fetch/read/cancel operations are counted; incomplete drain, deadline/clock failure, source/evidence mutation or failed final confirmation withholds selection. Bound violations and ordinary RPC failures are retained. This cap may yield no candidate; that outcome is final for this packet.

The standalone runner uses Node built-ins only. Freeze copies its complete owned source, tests, plan and retained upstream sources, verifies source/copy/source bytes and modes, and records exact Node identity before any RPC. STARTED and all raw request/response and derived files are exclusive and durable; a write-identity ledger is checked before sealing. The archived runner must be invoked with the exact externally supplied plan hash. No signing, broadcast, state/block override, target simulation or dependency installation occurs. The parent task explicitly authorized this bounded read-only selection after preparation controls.
