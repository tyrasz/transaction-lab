Updated October 27, 2026. The long-term goal remains active. **No representative 90% accuracy rate or superiority to Blockaid has been established.** This is a working prototype with narrow measured coverage, not a general EVM simulation or security product.

The app runs at http://127.0.0.1:5174/ without a wallet connection or Dynamic authentication. Version 0.12 adds experimental ordered two-to-four-call Ethereum sequences, with full validated state carried between calls and separate results for each step. Version 0.11's measured native ETH changes and nonzero values and version 0.10's automatic token balance and allowance checks remain available for single calls and supported sequence steps. Earlier explicit-query and automatic-query captures remain preserved as prior evidence below. The existing HyperEVM endpoints retain their semantics. Public RPC nodes execute EVM calls; the service owns interpretation, supported state measurements, validation and evidence retention. Security remains `not_assessed`. No signing or broadcasting occurs.

## Ethereum API and browser integration

`POST /api/evm/simulate` accepts flat `{chainId:1,from,to,data,value:"0",block?,queries?}` inputs. Omitting `queries` selects automatically; an explicit list retains the existing one-to-eight distinct canonical `balanceOf`/`allowance` behavior. Explicit `[]` and `null` are rejected. The block is `latest`, a canonical hexadecimal number, or a block hash; the gas limit is fixed at 5,000,000. Native value accepts canonical decimal wei from zero through uint256 maximum; senders must be code-free. Ordinary ETH transfers to code-free recipients are supported. No caller-supplied provider, fees, state overrides or metadata are accepted.

The browser defaults Ethereum to automatic checks, with the two selected deposit examples at their fixed parent-block hashes and custom transaction inputs. Advanced contains a manual-query toggle and preloaded example lists; lists are not sent unless that toggle is enabled. It shows each account's exact balances separately from owner/spender allowances, with unavailable values explicitly marked. Discovery coverage identifies retained candidates, selected/measured checks, omissions and incomplete scans. Wrapper and inner-vault share balances are never summed as user assets. Known token names and decimals are historical reference metadata, not current-state identity verification. Editing inputs or the query mode clears stale results and downloads; request fields and the network choice are locked while a call runs.

Candidates come from committed ERC-20-shaped events and direct token CALL frames, without a token registry. Matching a Transfer/Approval event or transfer/transferFrom/approve selector establishes a query hypothesis only. Selection prioritizes sender balances, sender-owned allowances, other balances, then other allowances, with lexical query ordering within each group. The eight-query limit retains additional candidates as omitted. Hard resource limits or malformed trace structure make discovery unavailable and withhold all automatic queries. Exact amounts still require separate validated before/after state reads; event values never become measured deltas. A complete scan does not establish complete economic coverage, and no candidates does not establish no effects.

Ethereum dependencies are isolated under `engines/standard-evm`. The server can start without them; `/api/config.standardEvm` then reports unavailable and the Ethereum action is disabled. Installation and a service restart enable it. The full main test suite requires these dependencies. `ETHEREUM_RPC_URL` is a server-only option, defaulting to `https://eth.drpc.org`; the existing HyperEVM provider option is independent.

The single-call transport bounds the entire request to 65 RPC calls, including one optional block-selection call, with 8 MiB per response body, 32 MiB shared response bodies, 145 seconds total and 25 seconds per call. The engine keeps its 64-call and 120-second scheduling bounds. Selected block-end state remains distinct from original transaction-position replay. The integration does not add a security verdict, fee estimate, complete asset inventory or broad accuracy claim.

Native ETH is reported separately in `nativeEffects` and `preview.nativeBalances`. Up to eight observed accounts receive pinned balance reads and isolated before/after BALANCE witnesses; amounts must agree with the full original state changes. Candidate CALL values never substitute for measurements. Omitted accounts and unavailable values remain explicit. Native measurements exclude outer transaction fees; creation/destruction and complete economic coverage remain unsupported.

### Ordered Ethereum sequences — 0.12.0

`POST /api/evm/simulate-sequence` accepts `{chainId:1,from,block?,calls:[{to,data,value,queries?},...]}` with two to four calls, one shared code-free sender and one block selection resolved once to a canonical hash. Each call uses canonical decimal wei and fixed gas of 5,000,000. Omit a call's `queries` for automatic discovery or supply its own explicit one-to-eight-query list. Caller-selected overrides, fee fields, providers and per-call sender/block changes are rejected before provider work. Only this route has a 384 KiB HTTP request-body limit; the single-call route remains 128 KiB.

Each `steps[i]` retains status, input, `stateSource`, and its full result with per-step `apiRequest`, source context, measurements and evidence. Successful validated original changes, including nonce and cleared storage, become the complete next starting state. Before queries read that step's starting state; after queries read the composed state. Query-only nonce increments are discarded. The first reverted, unsupported or unavailable step stops execution; later calls are explicitly skipped. A validated ordinary revert preserves earlier verified results. Shared state/header or final canonical failures invalidate earlier measurements together. This is an ordered unsigned simulation, not an atomic bundle: it has no signed-fee settlement, block/time advancement or rollback of earlier simulated successes because a later call reverts.

The sequence transport permits at most **258 RPC calls**, including optional block selection, with **8 MiB per body / 128 MiB total**, **265 seconds shared wall time** and **25 seconds per call**. The engine permits **257 calls**, including final canonical verification, with a **240-second scheduling window**; an already pending request can extend that by at most 25 seconds. Each step retains its narrower limits. There are no automatic retries or fallback state.

## HyperEVM current-call measurements

The service now validates configured token queries before and after an unsigned call. The original trace and complete state diff use the same fixed envelope and canonical block hash. Each balance or allowance query has an isolated execution trace and mutation diff on both sides; after-state queries reuse the complete original overrides. Configured USDC, hUSDC and variable-debt query paths, sender nonce transitions and unchanged query native balances must pass validation. Preparation, deadline or canonical failures invalidate shared measurements together.

This enables affected-account measurements for current simulations, including observed owners and recipients other than the submitter. It does not discover silent changes or arbitrary tokens. Path validation is not runtime-bytecode attestation. The supported profile is zero-native-value calls from code-free senders, with synthetic BASEFEE zero and omitted gas price. It does not validate signed transactions or estimate network fees. Limits are twelve distinct queries, 64 context RPC calls, bounded evidence and a 120-second scheduling window; a pending standard transport call can extend that window by at most 25 seconds.
