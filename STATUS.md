# Transaction Lab checkpoint — 0.9.0

Updated October 26, 2026. The long-term goal remains active. **No representative 90% accuracy rate or superiority to Blockaid has been established.** This is a working prototype with narrow measured coverage, not a general EVM simulation or security product.

The app runs at http://127.0.0.1:5174/ without a wallet connection or Dynamic authentication. Version 0.9 adds an experimental Ethereum API and network choice in the preview, verified with both selected deposits through the actual browser. The existing HyperEVM endpoints retain their semantics. Public RPC nodes execute EVM calls; the service owns interpretation, supported state measurements, validation and evidence retention. Security remains `not_assessed`. No signing or broadcasting occurs.

## Ethereum API and browser integration

`POST /api/evm/simulate` accepts flat `{chainId:1,from,to,data,value:"0",block?,queries:[{to,data}]}` inputs. The block is `latest`, a canonical hexadecimal number, or a block hash. One to eight distinct canonical `balanceOf`/`allowance` queries are required; the gas limit is fixed at 5,000,000. Only zero native value and code-free senders are supported. No caller-supplied provider, fees, state overrides or metadata are accepted.

The browser offers the two selected deposit examples at their fixed parent-block hashes, custom inputs and an editable advanced query list. It shows each account's exact balances separately from owner/spender allowances, with unavailable values explicitly marked. Wrapper and inner-vault share balances are never summed as user assets. Known token names and decimals are historical reference metadata, not current-state identity verification. Editing inputs clears stale results and downloads; request fields and the network choice are locked while a call runs.

Ethereum dependencies are isolated under `engines/standard-evm`. The server can start without them; `/api/config.standardEvm` then reports unavailable and the Ethereum action is disabled. Installation and a service restart enable it. The full main test suite requires these dependencies. `ETHEREUM_RPC_URL` is a server-only option, defaulting to `https://eth.drpc.org`; the existing HyperEVM provider option is independent.

The transport bounds the entire request to 65 RPC calls, including one optional block-selection call, with 8 MiB per response body, 32 MiB shared response bodies, 145 seconds total and 25 seconds per call. The engine keeps its 64-call and 120-second scheduling bounds. Selected block-end state remains distinct from original transaction-position replay. The integration does not add a security verdict, fee estimate, complete asset inventory or broad accuracy claim.

## HyperEVM current-call measurements

The service now validates configured token queries before and after an unsigned call. The original trace and complete state diff use the same fixed envelope and canonical block hash. Each balance or allowance query has an isolated execution trace and mutation diff on both sides; after-state queries reuse the complete original overrides. Configured USDC, hUSDC and variable-debt query paths, sender nonce transitions and unchanged query native balances must pass validation. Preparation, deadline or canonical failures invalidate shared measurements together.

This enables affected-account measurements for current simulations, including observed owners and recipients other than the submitter. It does not discover silent changes or arbitrary tokens. Path validation is not runtime-bytecode attestation. The supported profile is zero-native-value calls from code-free senders, with synthetic BASEFEE zero and omitted gas price. It does not validate signed transactions or estimate network fees. Limits are twelve distinct queries, 64 context RPC calls, bounded evidence and a 120-second scheduling window; a pending standard transport call can extend that window by at most 25 seconds.

## Experimental local execution

An isolated executor now uses pinned **EthereumJS 10.1.3** to run bytecode locally. It remains separate from the provider-backed API and browser preview, including the new Ethereum mode. Its sparse input adapter requires explicit account/code/storage facts; missing reads stop execution and roll back its changes. It does not construct initial state from expected call traces or state changes. [Executor documentation](engines/local-evm/README.md).

One fixed USDC `transferFrom` was captured from two public endpoints using 18 read-only requests. Both local runs succeed and match the provider outputs: 51,268 total gas under the declared intrinsic-gas rule, two entered call frames, one committed log, sender nonce +1 and three changed USDC storage slots. Owner and recipient balances change by −1.277067 and +1.277067 USDC; the allowance decreases by the same amount. This is **one selected transaction executed twice**, not two independent examples or a representative accuracy score. [Captured inputs](reports/local-execution-state/NOTES.md), [current local execution evidence](reports/local-execution-comparison-v2/NOTES.md).

All **58 isolated executor tests** pass. Independent review tightened source-block/parent binding, committed-state disposition, frame-field normalization and log ordering. The first sealed report and its exact original sources remain reproducible through the archived-source verifier; a separate second report records the corrected comparator with unchanged real-case outcomes. Both reports reproduce offline, including five separate synthetic fault controls. Latest result SHA-256: `c2eec4623db8890e21cdff02cdd31f0249c055e3485abdf026784c4ae81df803`.

The local profile remains zero-value unsigned Cancun execution with synthetic BASEFEE zero, no fee settlement and a provider-supplied sparse state witness. State is not cryptographically proven. HyperCore precompiles, CoreWriter, creation/destruction, blob context and uncaptured ancestor/state reads remain unsupported. Execution limits are cooperative; operating-system isolation is not implemented. The experiment therefore does not yet provide an arbitrary-transaction local simulation service.

## Experimental Ethereum deposits

The [standard EVM module](engines/standard-evm/README.md) accepts an explicit chain ID, canonical block hash, unsigned call and up to eight declared balance/allowance queries. It reuses complete original state changes for isolated post-state queries and validates query traces, nonce-only query mutations and both execution headers. Version 0.9 exposes its Ethereum profile through the API and browser described above. Its 31 focused tests pass; these include recorded provider data and synthetic negative controls, not 31 independent transactions.

The [Ethereum/Base capability survey](research/standard-evm/CAPABILITIES.md) recorded 48 public calls, including explicit method failures. Ethereum dRPC provided the required tracing and override features in that survey; the tested public Base endpoints did not. A separate [discovery packet](research/standard-evm/DEPOSIT-TARGETS.md) selected an Aave V3 USDC `supplyWithPermit` and a Kiln wrapper deposit into the Morpho V1 Steakhouse USDC vault. The latter is not Morpho V2, and its outer six-decimal shares differ from the inner eighteen-decimal shares.

The preserved [first capture](reports/standard-evm-deposits/NOTES.md) made 41 read-only RPC calls. Aave execution succeeded and all four requested measurements validated: wallet USDC −3,962.903485; aEthUSDC +3,962.903484; reserve USDC +3,962.903485; final wallet-to-Pool allowance 0→0 after permit use. This proves consistency of provider-supplied fields only. It does not independently authenticate the chain state or contract source. The existing HyperEVM parser remains unchanged.
