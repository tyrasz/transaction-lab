# Transaction Lab

An owned, read-only EVM transaction preview service. Version 0.12 adds experimental ordered two-to-four-call Ethereum (chain 1) sequences, with complete validated state carried between calls. Native ETH, token balance and allowance measurements remain available for single calls and supported sequence steps. A manual query list remains available. The existing HyperEVM (chain 999) paths cover Hyperlend USDC supply, withdrawal, variable-rate borrowing and repayment, with transparent handling of unsupported HyperCore execution.

The long-term objective is to outperform commercial simulation/security providers on measured correctness, coverage, latency, and explanations. No general superiority is claimed. The first milestone is an independently verifiable preview with public evidence and reproducible tests.

## Run

Requires Node.js 22 or later. Starting the HyperEVM service does not require external runtime packages. Ethereum previews use the optional, isolated pinned dependency under `engines/standard-evm`; install it before running the full main test suite or enabling Ethereum previews. The separate local executor has its own dependencies.

```sh
npm ci --prefix engines/standard-evm --ignore-scripts --no-audit --no-fund
npm test
npm run benchmark
npm start
```

Open http://127.0.0.1:5174/. The existing Dynamic comparison demo remains separate on port 5173.

Choose **Ethereum** in the Network selector for single-call Aave/Morpho examples or the ordered-call mode with the constructed Aave approve→supply example. Custom inputs remain available. Automatic checks are the default: the call's observed token events and calls supply candidates for up to eight balance or allowance queries. Advanced offers **Use a manual query list**; examples preload their recorded lists, but those lists are sent only when manual mode is enabled. The examples start at explicit historical parent-block hashes. Native ETH balances are shown separately, with outer transaction fees excluded. Token balances and allowances are displayed separately for each queried account; unavailable values are never shown as zero. The preview identifies omitted candidates and incomplete scans. Token names and decimal units are historical reference metadata, not newly verified contract identities.

If the optional Ethereum dependency is missing, the server still starts and HyperEVM remains available. Ethereum reports unavailable in `/api/config`, the browser disables its Simulate action, and both Ethereum simulation routes return 503. Install the dependency and restart the service to enable it.

The [experimental local executor](engines/local-evm/README.md) runs real bytecode with EthereumJS. Its original HyperEVM profile uses explicit sparse recorded inputs; a new Ethereum reference loads account/storage proofs and code lazily at one block hash, verifies them against the header's state root, and selects the corresponding fork rules. It is separate from the API and preview: those continue to use provider execution. Install its locked dependencies with `npm ci --prefix engines/local-evm --ignore-scripts`, then run `npm run test:local`. Missing or invalid state stops execution rather than supplying guessed values. Proof verification and the 122 passing local tests do not establish a broad transaction accuracy rate.

In the first [Ethereum local-reference comparison](reports/ethereum-local-reference/NOTES.md), the local engine matched the provider's status, return bytes, log, observed state changes and gas for one fixed USDC transfer. A second provider's proof-input attempt was unavailable and remains in the report. Local execution used only verified initial proofs/code and finished before the comparison output was requested.

The subsequent [lending comparison](reports/ethereum-lending-local-reference/NOTES.md) independently executes the selected Aave USDC supply and Morpho wrapper deposit. Both match all five compared channels, including gas of 189,775 and 1,413,682 respectively. Local execution demanded 288 proof/code requests in total before either product comparison began. These two selected development cases establish bounded agreement, not a representative accuracy rate, full call-tree equality or a security assessment.

With the server running, `npm run check:live` runs twelve read-only checks against public chain data and saves every API request and response in `reports/live/`. Wallet state and public-provider availability can change; a failed live check is retained for inspection. `npm run compare:providers` compares seven cases at one pinned block across the two documented public providers, preserving disagreements and evidence. `npm run check:historical` compares four fixed historical operations across those providers, retaining all eight calls and their underlying RPC evidence in `reports/historical-comparisons/` without retries. `npm run check:permissions` checks three observed approval/permit transactions across the same two providers, retaining all six attempts in `reports/permission-comparisons/`.

The default public RPC is `https://hyperliquid.drpc.org`. For dedicated infrastructure, set `HYPEREVM_RPC_URL` to an RPC with `debug_traceCall`, `debug_traceTransaction`, archive data, and callTracer log support. Provider credentials stay on the server and are not included in evidence. The service checks chain ID before each operation. Public endpoints can change limits or capabilities.

Ethereum uses `https://eth.drpc.org` by default. Set `ETHEREUM_RPC_URL` on the server to select another Ethereum provider with the required tracing, state-override and archive capabilities. Browser/API inputs cannot supply a provider URL. Both network settings are independent.

`npm run check:coverage` executes the [preregistered prospective pilot](research/coverage-evaluation/PLAN.md): it freezes the local source, waits for two future finalized HyperEVM blocks, keeps every transaction in the denominator, and attempts at most sixteen. It takes at least three minutes when selection succeeds and makes bounded read-only requests to both fixed public providers. Each run saves immutable product outputs before comparator adjudication under `reports/coverage-evaluation/`. This is a feasibility pilot; provider agreement and observed-pair matches are separate from complete transaction replay and all-effects accuracy.

`npm run check:coverage:v2` is the separate [ordinary/system enumeration protocol](research/coverage-evaluation/PLAN-V2.md). It preserves every unresolved occurrence, keeps unsupported system replay explicit, and withholds a combined denominator when identity or enumeration is incomplete. It adds the fixed official enumeration endpoint to the same bounded budget. Review and freeze its source before a live run. Its [first frozen pilot](reports/coverage-evaluation-v2/2026-10-26T07-52-08.304Z-60177bf2/NOTES.md) ended enumeration-inconclusive with no accepted accuracy denominator; the v1 pilot remains unchanged. The [archived baseline and offline verifier](reports/coverage-evaluation-v2-baseline-source/NOTES.md) reproduce that unchanged pilot independently of later application source changes.

HyperEVM measured current-state balances require `debug_traceCall` with callTracer, prestateTracer diff mode, state overrides and canonical EIP-1898 block-hash queries, plus hash-bound nonce, native balance and code reads. Each configured token query uses four isolated calls: its trace and mutation diff before and after the complete original-call overrides. The profile deliberately omits gas price and verifies synthetic BASEFEE zero; it does not estimate network fees. Historical measurements require archive `debug_traceCallMany` with block-hash and transaction-index state context. If capabilities or validation checks fail, the response retains available execution evidence and marks measurements unavailable.

HyperEVM current measurements accept at most twelve distinct queries and 64 context RPCs, with three slots reserved for canonical checks, 8 MiB per response and 32 MiB retained evidence. The context stops scheduling requests after 120 seconds and rejects late responses. With the standard RPC transport's 25-second timeout, pending calls can extend that window to at most 145 seconds; custom transports must enforce the same per-call bound.

```sh
HYPEREVM_RPC_URL=https://your-provider.example npm start
```

## Scope and interpretation

- A simulation does not sign or broadcast a transaction.
- HyperEVM current simulations select a block and use the same canonical EIP-1898 hash and unpriced envelope for the original execution trace and state diff. The supported measurement profile checks zero BASEFEE and the remaining header fields, requires a code-free sender and zero native value, and rejects contract creation/destruction. A provider that rejects the requested context is reported as unavailable; there is no silent fallback to latest.
- Historical traces use the original transaction hash and are separate from current-state simulations.
- HyperEVM asset arrays describe successful ERC-20 Transfer events involving the simulated sender. They are not a claim about exact portfolio balance changes.
- `accountEffects` lists all bounded observed transfer participants and configured permission roles, including owners other than the submitter. For each account/token it shows event totals separately from measured balances; unknown tokens retain raw units and debt remains a liability. Missing measurements are explicit. This view does not discover silent changes or every affected account.
- `affectedBalanceChanges` adds before/after reads for observed configured USDC, hUSDC and variable-debt participants, including accounts other than the sender. Historical and validated current contexts are supported. At most eight candidate pairs are accepted, including pairs already measured by the lending adapter. Reuse is verified through the same context cache; event totals never substitute for balances. Current reads validate the configured token/Pool paths and nonce-only query effects on both sides, including after proxy/dependency storage changes. This is address/path validation, not runtime-bytecode attestation. Unknown tokens and native effects remain outside this HyperEVM measurement scope; the legacy untraced current reader cannot enable these measurements.
- `balanceChanges` measures exact balances before and after a successful, reconciled Hyperlend operation. Supply covers sender/beneficiary USDC and hUSDC; withdrawal, borrowing and repayment additionally cover variable USDC debt and reserve custody. Current-state reads use the same block hash and timestamp, with the supported complete state diff applied only to ephemeral reads. Historical reads use the original block and transaction position. Reserve cash is labeled separately from user wealth.
- Shared balance, affected-account and allowance measurements are finalized together. If any consumer's canonical-block check fails, none is returned as measured; a later successful check cannot erase the failure. Raw shared evidence is retained after all consumers settle. An ordinary token-query failure remains local to that measurement.
- Hyperlend receipt-token mint events may include previously accrued interest. Principal and interest are reported separately when decoded.
- Deposit rounding is checked against the verified hUSDC implementation and its traced scaled-mint inputs. The response preserves requested principal, transferred principal, mint-implied principal and the exact difference.
- Security is `not_assessed`. EVM success must never become a `Benign` verdict.
- `permissions` separately records approval and permit requests, Approval events, and `transferFrom` calls for configured USDC/hUSDC contracts. Standard ERC-2612 permit and ERC-20 transferFrom decoding requires configured proxy implementation evidence. Owner, transaction submitter, immediate token caller/spender and recipient are distinct. A permit redemption deadline is not allowance expiry; a transfer amount is not a requested allowance. It identifies maximum allowances, revocations, false returns and calldata/event mismatches. Findings describe specific permission evidence. `allowanceChanges` separately queries final allowance before/after the whole current simulation or original historical transaction for observed verified pairs, including transfer-only pairs and unchanged allowances. It compares final state to ordered events without treating a mismatch as a maliciousness verdict. An unchanged allowance does not mean no spending occurred. Spender reputation and signing intent are not assessed.
- Variable-debt token mints are liabilities and are excluded from spendable incoming assets. `positionChanges` separates cash, position events and accrued interest. Repayments use the actual executed amount, which may be capped by outstanding debt.
- Unknown protocols and external HyperCore processing have explicit coverage limitations.
- Historical replay measures the configured token balances immediately before and after the original transaction. The original execution is independently replayed and compared with its recorded call trace and receipt events. Each balance query runs separately, with original block-header, sender-nonce and fee checks. Historical USDC/hUSDC allowances use the same validated original-position context, with separately verified allowance query behavior. Generic contract roots require original runtime-code evidence and an exact semantic replay; creation/destruction anywhere in the full trace, including reverted or temporary lifecycle operations, and unsupported account/code changes make measurements unavailable. Only supported legacy, access-list and fee-market transaction envelopes are accepted for measurement; blob and authorization-list semantics are outside scope.
- Pricing, malicious-contract detection, independent signature/domain/nonce validation, general NFT support, and complete asset discovery are not implemented. Ethereum's automatically selected or manually declared token queries do not establish complete economic coverage. The alternate bytes-signature USDC permit overload, Permit2, DAI-style permits and credit delegation are outside the current HyperEVM permit decoder.

The two public providers were also tested with stateful `eth_simulateV1`. That method is retained as capability evidence; the application uses the prestate-diff route so its primary trace and balance measurements share the original block context. See [capability evidence](reports/capabilities/STATEFUL-BALANCES.md).

The [standard EVM module](engines/standard-evm/README.md) powers the experimental Ethereum API and browser mode. It discovers query candidates from observed execution or measures a manually declared list, without depending on the HyperEVM token registry. It has its own pinned hashing dependency and test suite. Its selected development examples do not establish broad transaction accuracy. The completed [0.11 native packet](reports/standard-evm-native/NOTES.md) retains three separate single-call API captures: an ordinary ETH transfer, a swap with an internal ETH payment and an Aave control. All three execute successfully with verified context; four native accounts and eight token queries were measured using 79 read-only RPC calls. Exact archived replay and browser playback are documented separately. [Current checkpoint](STATUS.md#ordered-ethereum-sequences--0120).

The [0.12 sequence packet](reports/standard-evm-sequence/VERIFICATION.md) verifies three constructed Aave cases at the same historical block end using 112 read-only RPC calls / 457,073 response bytes. Supply alone reverted; approve→supply completed; a repeated third supply executed and reverted while preserving the verified prefix. Measured allowance was 0→3,962.903485→0 USDC; the wallet changed by −3,962.903485 USDC and +3,962.903484 aEthUSDC. All 112 exact wire responses reproduce through the archived API; 18 verifier controls and a [separate independent audit](reports/standard-evm-sequence/AUDIT-NOTES.md) pass. Current tests total 512 main and 102 engine checks. [Browser checks](reports/standard-evm-sequence/browser-checks.json) use saved-wire replay, adding no live observations. These selected examples do not establish broad accuracy or production reliability. The [earlier discovery](reports/standard-evm-sequence-discovery/continuation/NOTES.md), including its initial incomplete packet, remains unchanged.

Historical reads use a different route because block-end state is insufficient for a transaction in the middle of a block. The providers silently ignored `debug_traceCall`'s tested `txIndex` option, so the adapter uses validated `debug_traceCallMany` state context. It never inserts balance probes into the original transaction's execution sequence. See [historical state evidence](reports/historical-state/README.md).

## API

`POST /api/simulate` accepts `{chainId,from,to,data,value,block?}` for HyperEVM chain 999. `value` is a decimal wei string. `block` is `latest` or a hexadecimal block number. Its interpretation and the existing HyperEVM measurement rules are unchanged.

`POST /api/replay` accepts `{chainId:999,transactionHash}` for a confirmed historical HyperEVM transaction. Its original-position replay semantics are unchanged.

`POST /api/evm/simulate` accepts the flat Ethereum input `{chainId:1,from,to,data,value:"0",block?,queries?}`. Omit `queries` for automatic selection. To choose manually, supply one to eight distinct `{to,data}` entries encoding canonical `balanceOf(address)` or `allowance(address,address)` calls. Explicit `[]` and `null` are rejected rather than interpreted as automatic mode. `block` defaults to `latest`, or accepts a canonical hexadecimal number or a 32-byte block hash. Gas is fixed at 5,000,000. Native value is a canonical decimal wei string from zero through uint256 maximum; only code-free senders are supported. Callers cannot supply gas/fee fields, state overrides, provider URLs or token metadata. Input validation happens before provider requests.

`POST /api/evm/simulate-sequence` accepts `{chainId:1,from,block?,calls:[{to,data,value,queries?},...]}` with two to four calls. Sender and block are shared; block selection resolves once. Each call may omit `queries` for automatic discovery or provide its own explicit list. Gas, canonical decimal value and unsupported-field rules match the single-call route. Only the sequence route accepts HTTP bodies up to 384 KiB; the single-call route remains 128 KiB.

Each step retains its input, status, `stateSource` and full result, including per-step `apiRequest`, source context, discovery, preview, measurements and evidence. The complete validated state of each successful original call is carried into the next; measurement-query nonce changes are discarded. A reverted, unsupported or unavailable step stops the sequence and later steps are marked skipped. A validated revert preserves the verified prefix, while shared state/header or final canonical failure invalidates earlier measurements together. Calls are not atomic, fees are excluded, and block number/time do not advance. The sequence is not signed historical replay or a guarantee about a future mined bundle.

Automatic selection considers committed ERC-20-shaped Transfer/Approval events and direct token CALL frames shaped as transfer, transferFrom or approve. Matching an ABI shape is only a query hypothesis, not token identity or evidence of a balance change. Candidates are deduplicated and ordered by sender balances, sender-owned allowances, other balances, then other allowances, with lexical query ordering within each group. Up to eight are selected; additional candidates remain visible as omitted. Failed/static subtrees, NFT-shaped evidence and unsupported encodings are excluded. A malformed trace or a hard scan limit makes automatic discovery unavailable and withholds its queries. A completed bounded scan is not complete asset coverage; no candidates does not mean no assets changed.

Ethereum executes from the selected block's **end state**, including when a historical hash is supplied. It is not original-position replay. The response retains engine execution, measurements and evidence, plus the normalized `apiRequest`, block selection, account-specific `preview.queries` and `preview.nativeBalances`, timings and raw transport evidence. Automatic results also retain `discovery` candidates, selections, omissions, observations, diagnostics and scan limits. Exact amounts come from separate validated before/after queries, never event or requested-transfer totals. Unknown tokens retain raw integer units. Allowance owners, spenders and other token holders are distinct; a vault's holdings are never added to a depositor's assets. Security remains `not_assessed`.

Native ETH candidates come from committed CALL value transfers and reported balance changes. Up to eight accounts are measured separately from the eight token queries, ordered by sender, original recipient, then address. Each selected account has a pinned balance read and before/after BALANCE execution witnesses; those witnesses must agree with the complete state changes and committed CALL values and must change only the probe sender nonce. CALL values select and cross-check accounts; they never substitute for measured balances. Self-transfers remain visible with zero measured net change. Reverted descendants and inherited DELEGATECALL values do not become transfers. Newly funded code-free addresses require independent zero balance, zero nonce and empty-code reads. CREATE, CREATE2 and SELFDESTRUCT remain unsupported. Omitted accounts stay explicit, and shared state/header failures remove measured amounts. Native changes exclude network fees; signed-transaction settlement and full economic coverage remain unverified.

For a single call, the Ethereum transport permits at most 65 requests, including the optional one-request latest/number-to-hash selection before the engine's 64-request budget. It caps each response body at 8 MiB, all retained response bodies together at 32 MiB, the shared wall time at 145 seconds, and each call at 25 seconds. The engine retains its separate 120-second scheduling and parsed-evidence limits. Failures and unsupported measurements stay explicit; there is no fallback state or automatic retry.

Sequences have a shared maximum of 258 transport requests, including optional block selection, and 257 engine requests, including final canonical verification. Each body is bounded to 8 MiB and total response evidence to 128 MiB. The transport deadline is 265 seconds with at most 25 seconds per call; the engine stops scheduling after 240 seconds, and a pending call can extend that window by at most 25 seconds. Each step retains its narrower limits. Failures are retained without automatic retries or fallback states.

`GET /api/config` lists examples and capabilities. Its `standardEvm` object includes `available`, single-call `examples`/`capabilities` and `sequenceExamples`/`sequenceCapabilities`, or an unavailability reason. Ethereum examples include their complete request inputs and historical reference context. `GET /api/benchmarks` returns the latest deterministic benchmark. `GET /api/health` checks service availability.

The local HTTP service only exposes read-only operations. Its RPC wrapper also enforces a read-only method allowlist. It binds to loopback, caps request/trace sizes, limits concurrent simulations, and rejects cross-origin POST requests. Public deployment requires authentication, rate limits, operational hardening, and a separate deployment review.

Reports are saved in `reports/simulations/` with a maximum of 40 retained responses. Downloads preserve the complete request and evidence. Benchmark reports and fixtures distinguish observed chain data from synthetic negative cases.

Each API result includes an implementation version and a SHA-256 fingerprint of the server's loaded source files. Runtime reports are kept locally outside version control; public capability probes and regression fixtures are retained with the source.

The [lending evidence index](reports/lending-discovery/INDEX.md) links verified transactions, deployed source and raw responses. The [affected-account discovery index](reports/affected-account-discovery/INDEX.md) documents public examples where token owners, spenders and submitters differ, with raw evidence and retained provider inconsistencies. These examples do not establish user consent or maliciousness. The [security corpus intake](research/security-corpus/PLAN.md) contains three researched candidates, one admitted development effects reference, zero security scoring cases and zero blind holdouts; it is not a security detection score.
